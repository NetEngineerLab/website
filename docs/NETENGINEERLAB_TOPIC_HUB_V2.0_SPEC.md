# NetEngineerLab Topic Hub V2.0 统一设计规范

版本：2.0.0  
状态：实施规范草案  
适用范围：NetEngineerLab 网站的工程专题页、专题关联内容、首页专题入口及专题验收

## 1. 目的与产品原则

Topic Hub 是工程师完成一项工作任务的入口和资源导航，不是工具目录或关键词集合。它需要把问题、计算方法、工具、实例、故障处理和工程依据组织成一条可执行路径，让用户知道从哪里开始、下一步做什么，以及结果有哪些边界。

统一用户路径：

```text
明确任务 → 理解方法 → 计算或诊断 → 校核场景与故障 → 查阅依据 → 采取下一步行动
```

执行原则：

- 按用户要完成的工程任务组织资源，不按内部工具数量或文件类型堆链接。
- 每个入口提供清楚的下一步；计算结果应连接到验证、部署或排障动作。
- 只收录已发布、可访问且对该任务有直接帮助的资源；没有的内容明确标为待建设，不伪造完整度。
- 一个 URL 对应一个清晰的主题边界。重复、过宽或仅为注册表占位的页面不能作为独立权威专题发布。
- 专题、指南、工具和 GitHub 工程资料互相链接；新增、改名、迁移或退役资源时，同一变更必须复核专题聚合和导航。

本规范扩展并具体化 [`NETENGINEERLAB_TOPIC_GROWTH_GITHUB_SYNC_STANDARD_V1.1.md`](NETENGINEERLAB_TOPIC_GROWTH_GITHUB_SYNC_STANDARD_V1.1.md)，V1.1 中关于主题资产、搜索质量和 GitHub 同步的要求继续有效。

## 2. 专题成熟度与发布状态

每个专题在项目跟踪记录中使用以下一种状态。状态表示可验证的内容成熟度，不是营销标签。

| 状态 | 判定标准 | 对用户的呈现 |
| --- | --- | --- |
| `Candidate` 候选 | 有明确工程任务和至少一个真实资源，但主题边界或资源组合尚未验证 | 可在内部规划，不新增索引型薄页 |
| `Foundation` 基础 | 有专题概述、至少一个可用工具或指南、明确路径和限制；关键内容仍有缺口 | 若发布，清楚显示现有覆盖范围，不宣称完整 |
| `Workflow` 工作流 | 完成第 4 节的核心路径，至少覆盖理解、执行和校核/排障；导航和资源清单已核对 | 可作为正式 Topic Hub 推广 |
| `Authority` 权威 | 工作流达标，并有足够场景指南、案例、可靠依据和跨资源闭环；持续维护负责人明确 | 可作为核心主题入口和长期搜索资产 |

状态必须有证据：记录页面、工具、指南、案例和验证结果的链接。不能只因页面较长、工具较多或搜索流量较高而升级。

## 3. 信息架构与 URL 规则

- 英文主路径：`/topics/<topic-slug>/`。
- 中文路径：`/zh/topics/<topic-slug>/`。仅在中文内容达到可用质量并经过语言复核后建立对应页面。
- slug 使用稳定、简洁、主题明确的 kebab-case。已收录 URL 不因标题润色而随意更改。
- 每个语言版本使用唯一 title、description、H1、canonical 和正确的 hreflang 配对；不支持的语言不得生成空壳翻译页。
- sitemap 只列出正式、可索引的规范专题 URL；重定向、弃用页和内部占位页不得以独立专题重复收录。
- 首页只突出一组经过治理的核心专题入口；工具目录仍可作为工具发现入口，两者承担不同任务。
- 旧 URL 处理必须先核查收录和外链：保留有独立价值的页面；重复页面合并到规范 URL，并设置合适的永久重定向和站内链接更新；不以删除制造断链。

## 4. 标准 Topic Hub 页面结构

页面以任务路径为主线，按专题实际情况采用以下区块。至少必须有概述、任务入口、推荐路径、真实资源清单和工程边界。

1. **专题概述**：说明适用对象、问题边界和用户可完成的结果，避免泛化承诺。
2. **从这里开始**：链接到一篇主指南或最合适的首次操作，并说明为什么从这里开始。
3. **按任务选择路径**：以用户问题为标签，每条路径给出动作、资源和结果。例如：

   | 用户任务 | 推荐步骤 |
   | --- | --- |
   | 设计新的 PON 链路 | 明确等级与预算 → 计算分光/链路损耗 → 对照接收功率与设备规格 |
   | 排查 ONU 收光偏低 | 核对 ONU 接收功率 → 用 OTDR 定位事件 → 与链路预算和设计值比较 |

4. **计算与规划**：工具卡说明输入适用条件、主要输出及核心假设，链接到工具中的方法说明。
5. **常见场景和案例**：按决策问题组织指南、示例与案例，标记场景条件和结论边界。
6. **故障、冗余与风险校核**：提供适用的故障态、N-1、恢复或异常诊断路径；不适用时说明原因。
7. **标准和工程资源**：列出有版本、出处或发布日期的规范、厂商资料及 GitHub 速查文档，并说明其用途。
8. **推荐学习/执行顺序**：使用有序步骤，让首次访问者能按顺序完成工作。
9. **当前专题资源**：列出全部已发布且直接相关的站内资源和公开 GitHub 文档；清单必须与资产登记一致。
10. **工程边界与 FAQ**：说明输入数据、假设、现场验证要求及不能由工具单独判定的事项。
11. **相关专题**：只链接相邻任务，并说明交叉关系，避免无关的站内链接。

不适用区块可以省略，但页面需保留完整任务路径；不得用空标题或通用占位文案填充结构。专题页应在手机和桌面端均可读、可键盘访问，并遵循站点组件与视觉系统。

## 5. 专题资产模型与链接闭环

每个核心专题应维护一份可审计的资产清单（可由内容注册表、专题配置或验证脚本生成），至少包含：资源 ID、标题、规范 URL、语言、类型、状态、所属专题、任务角色、最后复核日期。已发布资源不得只存在于人工记忆或单页硬编码中。

资产类型包括：Topic Hub、主指南、问题指南、计算器/规划器、案例、图表、GitHub 速查资料、标准/厂商来源。每项资源需有明确归属；跨专题复用时可登记多个主题，但须说明关联，避免复制内容。

最低闭环：

```text
Topic Hub ↔ 主指南 ↔ 工具
       ↘ 场景/案例 ↔ 故障或校核内容
       ↘ GitHub 速查资料与权威来源
```

- 专题到工具：说明使用场景和适用输入；工具到专题：提供继续学习或相关流程入口。
- 指南应连接对应工具、专题及相邻问题页；重要工具结果区应告诉用户下一步操作。
- GitHub 外链必须使用真实公开 URL；仓库内相对路径不得作为网站用户链接。GitHub 资料不能逐字复制网站长文。
- 外部标准/厂商链接应直达相关资料，优先使用一手来源，保留名称、机构及必要版本信息。
- 所有内部链接必须指向有效规范路由；失效链接、草稿路由或未发布资源不得显示为可用入口。

## 6. 多语言、搜索与可访问性要求

- 英文和中文页面须有同等工程决策价值，而非逐字翻译后留下过时工具名、缺失链接或不自然术语。
- hreflang 只连接内容实质对应的语言页，双向一致；没有对应页时不输出虚假的配对。
- 每页应有独立且准确的 title、meta description、一个清晰 H1、canonical、适当的 CollectionPage/WebPage 结构化数据和社交分享元数据。
- 页面正文应先回答专题要解决的问题，内容以工程任务、方法和限制为中心；不得为 SEO 重复同一意图的薄页面。
- 页面必须包含可见键盘焦点、语义化标题层级、描述性链接文本、足够对比度和移动端适配；不得仅以颜色表达状态。
- 页面性能、Cookie/隐私控件及共享站点页头页脚需符合站点当前生产要求。

## 7. 治理与变更流程

任何新增或变更工具、指南、案例、标准来源、GitHub 文档、slug、语言版本时，提交者必须在同一变更中：

1. 更新资产登记和相关专题页的任务路径、推荐顺序及当前资源清单。
2. 更新对应资源的返回链接，并检查它们是否仍指向正确专题。
3. 检查 canonical、hreflang、sitemap、导航、结构化数据和重定向（按变更类型适用）。
4. 运行专题路由、内部链接和多语言一致性检查；记录检查结果。
5. 更新专题成熟度证据、复核日期和维护责任人。

专题负责人负责内容边界和资源完整性；工具负责人负责公式、输入输出与方法说明；发布负责人负责路由、元数据、索引、可访问性和构建验收。小团队可由同一人承担多个角色，但验收证据仍要齐全。

## 8. 验收门槛

专题进入 `Workflow` 或 `Authority` 前逐项通过：

- **任务完整性**：至少一条清楚的“理解 → 执行 → 校核/排障”路径，步骤有实际可访问资源支撑。
- **资源完整性**：专题所归属的所有已发布相关资源均列入资产清单和专题页；不存在孤立核心工具或指南。
- **工程可信度**：关键公式、假设、单位、设备边界和风险说明可追溯；外部依据来自可靠来源。
- **链接与路由**：内部链接返回成功；canonical、hreflang、sitemap、重定向状态符合第 3、6 节。
- **语言与体验**：已提供语言版本经过内容复核；移动端、桌面端、键盘和语义检查通过。
- **维护性**：每项资源有明确状态，负责人和最近复核日期可查，更新流程可执行。

验收至少保留：URL/资源清单、自动链接检查结果、各语言元数据检查、关键视口的视觉或浏览器检查、工程内容复核记录。任何必需检查失败或未运行，不得标为通过。

建议用以下简表记录结果：

| 检查项 | 结果 | 证据/缺陷 | 负责人 |
| --- | --- | --- | --- |
| 任务路径 | Pass / Fail | 资源 URL 或缺口 |  |
| 资产清单与闭环 | Pass / Fail | 登记及反向链接 |  |
| 路由、搜索元数据 | Pass / Fail | 检查报告 |  |
| 工程与语言复核 | Pass / Fail | 复核记录 |  |
| 浏览器与可访问性 | Pass / Fail | 视口/检查结果 |  |

## 10. 实施顺序

1. **治理现有 URL**：盘点 `website/data/content-registry.json`、`scripts/build-topic-hubs.js` 的生成关系、所有 `/topics/` 生产路由、索引状态、反向链接和语言版本，确定每个主题的规范 URL；先标记重复页，不立即删除。检查 `scripts/topic-growth-audit.js` 的覆盖范围，目前它主要审计交换机专题，不能代替全站验收。
2. **完成 PON / Optical Network Hub**：这是工具和工作流底座较丰富、目前专题聚合明显不足的优先对象。以用户任务串联设计预算、分光/损耗计算、接收功率检查和 OTDR 故障定位，并核对各工具的实际路由与中英文支持。
3. **统一首页入口**：只展示已发布、通过 `Workflow` 验收的核心专题；增加或调整入口时，同时明确各专题用户价值和维护状态。
4. **补齐 Data Center 与 Telecom Power**：按同一验收表补资源清单、任务路径、互链及多语言元数据。
5. **建立持续检查**：在内容变更和发布流程中检测未登记资源、孤立核心页、断链、重复规范 URL、过期链接与不一致语言路由。

除非具体审计证明必要，不重写已有成熟页面；以增量补齐和统一治理为主。

## 11. 与现有仓库结构的映射

- 网站 hub：`website/topics/<slug>/index.html`；中文页：`website/zh/topics/<slug>/index.html`。
- 主题和关联资产：优先复用 `website/data/content-registry.json` 及现有配置/生成机制，避免建立第二份互相漂移的事实来源。
- 路由和索引：检查 `website/data/sitemap-routes.json`、生成脚本及最终 `website/sitemap.xml` 的实际职责，不绕过现有流程手工制造不一致数据。
- 共享呈现：复用 `website/assets/css/topic-hub.css`、站点页壳和现有组件；视觉变更需覆盖代表性移动和桌面视口。
- 工程资料：GitHub 速查文档放入现有 `docs/guides/<domain>/` 结构，并从专题页链接公开地址。
- 本规范只定义产品和内容验收，不规定未经代码审查的具体重构方式；若注册表、sitemap 生成器或构建系统存在差异，先以当前生产管线为准并记录决策。
