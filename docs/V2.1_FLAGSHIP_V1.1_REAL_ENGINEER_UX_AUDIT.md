# NetEngineerLab V2.1 Flagship V1.1 — Real Engineer UX Audit

**Modified:** 2026-09-05 18:08:01  
**Scope:** Network Change Planner & MOP Generator  
**Constraint:** UX/product-depth only. No new configuration domain, renderer, parser, device model, or automation capability was added.

## Audit goal

A first-time network engineer should be able to understand the page and move through this path with minimal hesitation:

1. Identify whether the page contains example or production data.
2. Paste/confirm current running configuration.
3. Define device, aggregate members and VLAN intent.
4. Build the change plan.
5. Understand risk and semantic delta.
6. Locate forward and rollback configuration quickly.
7. Follow the execution runbook.
8. Paste post-change evidence and understand the final decision.

The product target is a 3–5 minute first-use path for a prepared engineer. This repository audit validates information architecture, state guidance, navigation, field clarity and automated contracts. It does **not** claim a statistically valid human stopwatch result; that requires an observed engineer session.

## Findings and corrections

### 1. Example data could be mistaken for production input — corrected

**Before:** A representative scenario was loaded on page entry, but the training-data boundary was visually weak.  
**Risk:** An engineer could scan the populated form and miss that the running config is only an example.  
**Change:** Added an explicit `EXAMPLE DATA / 示例数据` badge, safety warning, and status message telling the engineer to replace the running config before real use.

### 2. Aggregate member inputs were ambiguous — corrected

**Before:** Each member row displayed two numeric inputs, while `member` versus `physical port` existed mainly in ARIA labels.  
**Risk:** First-time users could reverse member/port values, especially on StackWise or Virtual Chassis devices.  
**Change:** Added visible sub-labels for `Stack / chassis member` and `Physical port` in English and Chinese.

### 3. After plan generation, the next reading order was not explicit — corrected

**Before:** Risk, diff, forward, rollback, runbook, verification and MOP were all present but required vertical scanning.  
**Risk:** Users could jump directly to forward configuration without reviewing risk or rollback.  
**Change:** Added a dynamic `Next` callout and direct section navigation: Risk → Forward → Rollback → Runbook → Verify → MOP.

### 4. Guided-step completion did not fully reflect real state — corrected

**Before:** Step 1 appeared complete by default and Step 2 did not reliably show completion after valid input.  
**Risk:** The four-step guide looked decorative instead of operational.  
**Change:** Step 1 now follows running-config presence; Step 2 follows member/VLAN/native readiness; Step 3 follows successful plan creation; Step 4 follows verification evaluation.

### 5. Verification evidence completeness was invisible — corrected

**Before:** Engineers could paste some outputs and click Evaluate, but there was no live count showing how much evidence had been supplied.  
**Risk:** `INCONCLUSIVE` could feel surprising even though the engine was behaving correctly.  
**Change:** Added a live `n / total checks have evidence` indicator with empty/partial/complete states.

### 6. Mobile handoff from input to result required extra navigation — corrected

**Before:** After tapping Build Change Plan on a narrow screen, the page updated but did not explicitly move to the result area.  
**Change:** On viewports <= 920px, successful plan creation now scrolls to the result card. Desktop two-column behavior is unchanged.

### 7. Rollback discoverability needed stronger emphasis — corrected

**Change:** Added a direct Rollback shortcut, scroll targets and subtle visual differentiation while retaining the same rollback engine output.

## What was deliberately NOT changed

- No new vendor support.
- No new device model.
- No BGP/OSPF/STP/QoS management.
- No automatic device login or command execution.
- No change to Minimal Delta semantics.
- No change to risk scoring rules.
- No change to rollback calculation.
- No change to verification decision rules.

This preserves the rule: **UX depth before feature breadth.**

## Recommended human acceptance script

Use a network engineer who has not seen the page before. Do not explain the UI. Ask them to:

1. Identify whether the loaded configuration is an example.
2. Replace it with a prepared fixture or keep the demo for a trial run.
3. Confirm Member A/B values and what each number means.
4. Build the plan.
5. State the risk band and the two most important risk reasons.
6. Find the rollback configuration without being told where it is.
7. Find the execution runbook.
8. Paste supplied post-check fixtures.
9. Explain why the final result is PASS / INCONCLUSIVE / ROLLBACK_REQUIRED.

**Target:** complete the guided demo path in 3–5 minutes with no external explanation and no critical input mistakes.
