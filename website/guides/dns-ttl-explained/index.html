DNS TTL Explained: Seconds, Minutes, Hours and Real-World Examples

A DNS TTL is a time-to-live on one resource-record set. The unit in the DNS message is seconds. A TTL calculator, or DNS TTL calculator, is only doing that unit conversion plus whatever cache-age inputs you add. The conversion itself is exact. The moment a changed record becomes visible is not.

What the seconds count

RFC 1035 defines the TTL as a 32-bit unsigned integer counted in seconds. A value of zero means the response is not cached beyond the current transaction. Nothing in that definition says that a 300 second TTL, a 600 second TTL or an 86400 second TTL will refresh every resolver at once.

TTL to minutes and TTL to seconds

TTL to minutes is seconds divided by 60. TTL to seconds is minutes multiplied by 60, or hours multiplied by 3600. Both directions are integer arithmetic for the five values below, so each row can be checked without rounding.

300, 600, 3600, 14400 and 86400 seconds

A 300 TTL in minutes is 300 / 60 = 5 minutes, which is 1/12 of an hour. A 600 TTL in minutes is 600 / 60 = 10 minutes, which is 1/6 of an hour. 3600 / 60 = 60 minutes = 1 hour. 14400 / 60 = 240 minutes = 4 hours. An 86400 TTL in minutes is 86400 / 60 = 1440 minutes = 24 hours. The reverse check is the last column: 5 x 60 = 300, 10 x 60 = 600, 60 x 60 = 3600, 240 x 60 = 14400, and 1440 x 60 = 86400.

Operators type these values before a migration or on a zone that should change slowly. They are examples of the arithmetic, not a recommended propagation schedule and not a default from RFC 1035.

One cache is not the network

Remaining TTL is local to the resolver that stored the answer. Take an A record whose authoritative TTL is 3600 seconds, and three resolvers, as an example only:

  1. Resolver A stored it 600 seconds ago. Remaining TTL = 3600 - 600 = 3000 seconds = 50 minutes.
  2. Resolver B stored it just now. Remaining TTL = 3600 - 0 = 3600 seconds = 60 minutes.
  3. Resolver C still holds the previous answer, which it cached when the TTL was 86400 seconds, and 3600 seconds have elapsed there. Remaining TTL = 86400 - 3600 = 82800 seconds = 23 hours.

Those three clocks are not one propagation time. The old TTL still governs any cache that stored the previous record set. A different record at the same name, such as an MX with a 3600 second TTL beside an A with a 300 second TTL, expires on its own clock.

Negative caching is a separate timer. RFC 2308 sets the TTL of an NXDOMAIN or NODATA answer to the lesser of the SOA MINIMUM field and the SOA record's own TTL. If a zone shows an SOA record TTL of 600 seconds and a MINIMUM of 3600 seconds, the negative answer uses 600 seconds, which is 10 minutes. If the zone shows different SOA fields, the result is different. That 10 minutes does not apply to a positive A record, and it is not a fixed interval for every zone.

Changing the record is not waiting out a TTL

Publishing a new answer at the authoritative servers does not rewrite recursive caches. Each cache keeps the set it stored until that entry's remaining TTL reaches zero, unless that resolver's own policy does something else. Some resolvers cap the TTL they keep. RFC 8767 permits serving a stale answer when the resolver cannot refresh it from the authoritative servers. Delegation changes, DNSSEC validation and client or application caches can move the time a user sees the new data as well.

Lowering the TTL before a change only affects caches that store the record after the lower value is visible at the authoritative servers. Caches that already stored the longer old TTL keep that longer value until their own remainder runs out. Do not read "the TTL expired" as "the network is now in sync."

The DNS TTL calculator estimates a planning window from the current TTL, the time already cached, a negative-cache TTL and an authoritative delay that you type. That window is a heuristic for those inputs. It is not a measured global cutover, and this guide does not add a second formula for one.

Public sources: RFC 1035 RFC 2308 RFC 8767 RFC 9199. This page uses definitions that can be re-read there. It does not turn any second count into a network-wide synchronization time.

Frequently asked questions

What is a DNS TTL?

RFC 1035 defines a resource-record TTL as a 32-bit count of seconds. It limits how long one resolver may reuse the record set it stored. It is not a clock for worldwide DNS synchronization.

How many minutes is a 300 second DNS TTL?

300 divided by 60 is 5 minutes. The same step gives 10 minutes for 600 seconds, 60 minutes for 3600 seconds, 240 minutes for 14400 seconds, and 1440 minutes for 86400 seconds.

How do I convert a TTL in minutes back to seconds?

Multiply the minutes by 60. Five minutes is 300 seconds, ten minutes is 600 seconds, 60 minutes is 3600 seconds, 240 minutes is 14400 seconds, and 1440 minutes is 86400 seconds.

Does TTL expiry mean every resolver has the new record?

No. Each recursive cache keeps its own remaining TTL. A resolver that still holds an older 86400 second answer can return it after a resolver that stored a 300 second answer has expired. RFC 8767 also permits a stale answer when a refresh fails.

Is the remaining TTL the same number as the old TTL?

Only for a cache entry that was just stored. Remaining TTL is that entry's stored TTL minus the time already elapsed at that resolver. An MX record beside an A record carries its own TTL.

Does negative caching use the address-record TTL?

Not by default. RFC 2308 takes the negative-answer TTL from the lesser of the SOA MINIMUM field and the SOA record TTL. Those fields come from the zone you query. They are not the positive A-record TTL.
