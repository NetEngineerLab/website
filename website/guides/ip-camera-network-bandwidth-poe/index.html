CAMERA NETWORK BANDWIDTH

How to evaluate PoE IP camera data throughput

Add only the streams that use the same link at the same time. Camera network bandwidth, in Mbit/s, is that sum times an overhead allowance you write down. A PoE switch power budget is a separate calculation in watts.

Bandwidth for IP cameras is the encoded video that actually traverses the link you are sizing, plus a stated allowance for headers and short bursts. PoE power does not set that number. The worked figures below are scenario examples. They are not a universal camera bitrate.

1. Bandwidth formula

For one path, in megabits per second:

Path payload (Mbit/s) = Σ concurrent streams on that path
When every camera contributes the same streams: payload = camera count × (sum of those per-camera stream rates)
Planning load = payload × overhead allowance

Units: each stream rate is the average encoded bitrate in Mbit/s (megabits per second, decimal). Camera count is a count of cameras whose streams use this path during the same busy hour. The overhead allowance is dimensionless. This guide’s worked case uses 1.15. That factor is a planning assumption for protocol headers and short peaks. It is not an IEEE 802.3 requirement.

If the bitrate you enter was already measured on the switch port, it may already include Ethernet, IP, UDP and RTP headers. Do not multiply that measurement by 1.15 again. If the number is the camera’s encoded video setting, the headers are still outside it, and an allowance belongs in the plan.

Keep the average recording rate and the short peak separate. Storage follows the average of the streams that are recorded. The uplink must also survive the busy-hour peak you design for.

2. Camera count times one stream rate

Use count × rate only when each camera adds that one rate to the same path. A site total is not the uplink of one access switch unless every camera homes on that switch.

3. H.264 and H.265

H.264 and H.265 are different video coding standards. ITU-T H.264 specifies Advanced Video Coding. ITU-T H.265 specifies High Efficiency Video Coding. A later codec can use fewer bits for a similar picture in some scenes. The difference is not a fixed savings percentage.

Do not apply a fixed savings percentage when you change codecs. Scene motion, GOP length, bitrate control and the vendor profile all move the result. Axis’s white paper on bitrate control says variable-bitrate streams grow when the scene gets busy, and it does not publish one percent that fits every camera. Enter the average bitrate of the profile you will actually record and view.

The IP Camera Network Planner still on this site estimates per-camera Mbit/s as megapixels × a codec coefficient × (frames per second ÷ 15) × 8. The coefficients in that page are 0.075 for H.264, 0.045 for H.265 and 0.24 for MJPEG. Those coefficients are an internal first-pass model. They are not a measured camera, and the gap between 0.075 and 0.045 must not be reused as an H.265 savings percentage. Replace the estimate with the configured or measured bitrate before a design decision. This guide does not change that planner.

4. Main stream, sub stream and the real rate

Many cameras publish a main stream for recording and a sub stream for live view. Add a stream only if it is enabled and it uses the path you are sizing, at the same time as the others.

  • Example main stream, recorded to an NVR upstream of the access switch: 4.0 Mbit/s average, unicast.
  • Example sub stream, viewed by one operator PC that is also upstream of the same switch: 0.5 Mbit/s average, unicast, concurrent with the main stream.
  • Per camera on that uplink: 4.0 + 0.5 = 4.5 Mbit/s. This is still an example, not a datasheet.

If the operator PC is on the same access switch, the sub stream does not use the uplink. The uplink payload is then camera count × 4.0 Mbit/s only. Do not add the sub stream in that case.

Do not count the same main stream twice. The access uplink carries it once. An aggregation link carries the sum of the access uplinks that feed it, which is those same streams once, not again on top.

Recording storage uses the streams the recorder stores. In this example that is the 4.0 Mbit/s main stream, not the 0.5 Mbit/s sub stream, unless you also record the sub stream. Network headers are not added to that storage line unless the recorder stores them.

5. Switch uplink

Size each access uplink for the cameras on that switch, not for the whole site. Planning load = payload × overhead allowance. This guide’s worked allowance is × 1.15. A growth margin is a second factor. The worked case uses × 1.20 after the overhead factor. Write both down so they are not applied twice to a number that already includes them.

The IP Camera Network Planner applies its own × 1.20 to the estimated encoded total and labels the result as bandwidth including 20% protocol headroom. It then looks for the smallest link in the set 1, 10, 25, 40 or 100 Gbit/s whose capacity is at least twice that total, and it reports remaining capacity as that link’s Mbit/s minus the total. That is a dual-uplink sketch inside the planner. It does not prove the two links are independent, and it does not use the × 1.15 factor from this guide. Do not multiply a planner result by 1.15 again.

6. Redundancy and margin

N-1 means one named component can fail and the service still meets the target you wrote down. For the uplink, the surviving path must carry the load that moves onto it. A single uplink has no surviving path. Two 1 Gbit/s links meet an N-1 bandwidth check only when either link can carry the planning load by itself, and only for bandwidth. Stack control, power supplies and the NVR are separate failure domains.

Keep the allowances separate:

  • Protocol and burst allowance on data: × 1.15 in this guide’s example, or the planner’s × 1.20 on its own estimate. Not both on the same number.
  • Growth allowance on data: × 1.20 in the worked case, applied after overhead. This is a project choice, not a standard.
  • PoE watt headroom, below, is a percent on watts. It does not change Mbit/s.

7. PoE power is not data bandwidth

IEEE 802.3 defines how a power sourcing equipment port delivers DC power to a powered device. It does not define the camera’s video bitrate. A switch can pass the watt budget and still fail remote voltage, or pass voltage and still congest the uplink.

The PoE power budget calculator, which this page does not modify, uses:

Source watts per device = PD watts ÷ (1 − cable-loss fraction)
Required switch budget = source watts × device count × (1 + headroom fraction)

Cable-loss fraction and headroom fraction are the percents you enter, divided by 100. The calculator also requires device count ≤ PoE port count, and PD watts ≤ the class limit coded for the selected standard: 12.95 W (802.3af), 25.5 W (802.3at), 51 W (802.3bt Type 3) or 71.3 W (802.3bt Type 4). Those are the watts at the powered device. The matching PSE class powers in the same calculator are 15.4 W, 30 W, 60 W and 90 W. Public summaries of IEEE 802.3 list the same pairs. The loss percent is a planning input, not a full channel simulation.

The IP Camera Network Planner uses a different watt line: camera count × entered watts × 1.25. That single 25% factor is not the same as loss and headroom entered separately. Do not mix the two results.

Remote voltage is a third model, in the PoE voltage drop calculator. It starts from conductor resistance for the selected AWG at 20 °C, scales it by 0.00393 per °C away from 20 °C, builds loop resistance as two conductors × length ÷ pairs, adds the contact resistance you enter, then solves the current for the load power and the delivery efficiency you enter. A passing watt budget does not answer that voltage.

8. Example: 16 cameras, one access switch

Example, not a camera datasheet. Sixteen fixed cameras. Each sends one unicast main stream of 4.0 Mbit/s to an NVR upstream of this switch, and one unicast sub stream of 0.5 Mbit/s to an operator PC that is also upstream. Both streams are concurrent. Audio is not included. No other traffic is on the uplink.

  1. Payload = 16 × (4.0 + 0.5) = 72.0 Mbit/s.
  2. Overhead allowance × 1.15, this guide’s assumption: 72.0 × 1.15 = 82.8 Mbit/s.
  3. Growth × 1.20 after that, also an assumption: 82.8 × 1.20 = 99.36 Mbit/s.
  4. A single 1 Gbit/s uplink is nominally 1000 Mbit/s, so the arithmetic fits in the normal state. N-1 does not: there is no second link. Two independent 1 Gbit/s links would each need to carry 99.36 Mbit/s after one fails. That check is only the bandwidth arithmetic.

If the operator PC is on this same switch, drop the sub stream from the uplink: 16 × 4.0 = 64.0 Mbit/s, then 64.0 × 1.15 = 73.6 Mbit/s, then 73.6 × 1.20 = 88.32 Mbit/s. Do not report 99.36 Mbit/s for that path.

Storage of the recorded main stream only, decimal units (1000, not 1024): daily gigabytes per camera = 4.0 × 86,400 ÷ 8 ÷ 1,000 = 43.2 GB/day. Sixteen cameras: 691.2 GB/day. Thirty days: 20,736 GB = 20.736 TB. This line does not include the 0.5 Mbit/s sub stream, RAID, or the × 1.15 network allowance. One hundred cameras at the same single 4.0 Mbit/s stream, with no sub stream recorded, are 4.32 TB/day and 129.6 TB in 30 days.

Power for the same sixteen cameras, still separate from the bitrate. Enter 12 W at the powered device, 15% cable loss, 20% headroom, and 802.3at in the PoE power budget calculator: source watts = 12 ÷ 0.85 = 14.1176 W; required budget = 14.1176 × 16 × 1.20 = 271.06 W. The same inputs for 24 cameras require 406.59 W. A 370 W switch passes 16 cameras and fails 24 on watts. Neither result changes the 72.0 Mbit/s.

Voltage is another input set, not this 12 W camera. The published 90 m example in the voltage calculator uses 25.5 W, 48 V source, 90 m, two pairs, 45 °C, 0.3 ohm contact resistance, 90% delivery efficiency and an entered floor of 42.5 V. With those inputs the calculator returns 37.87 V at the far end on 26 AWG (10.13 V drop, below the floor) and 43.51 V on 23 AWG (4.49 V drop, above the floor). UNH-IOL’s Clause 33 powered-device suite, citing IEEE Std 802.3-2012 Table 33-18, describes a Type 2 input range of 42.5 V to 57 V and a Type 1 range of 37 V to 57 V. The 42.5 V floor in that example is the Type 2 lower bound used as an entered check. It is not a measured certification of a cable, and a Type 1 device can use a lower floor.

Planner cross-check, defaults on that page, not this 16-camera example: 2 megapixels, H.265 coefficient 0.045, 15 frames per second, 100 cameras, 15 W, 30 days. Per camera = 2 × 0.045 × (15 ÷ 15) × 8 = 0.72 Mbit/s. Total after the planner’s × 1.20 = 86.4 Mbit/s. Watt line = 100 × 15 × 1.25 = 1875 W. Raw storage = 86.4 × 30 × 0.0108 = 27.9936 TB, shown as 27.99 TB. The line labeled usable is that figure ÷ 0.85. One decimal terabyte per day at 1 Mbit/s is 0.0108 TB, because 1 Mbit/s × 86,400 s ÷ 8 bit/byte = 1.08 × 1010 bytes. The planner folds its 20% network allowance into that terabyte line. Do not treat 0.72 Mbit/s as the 4.0 Mbit/s example above.

10. Common mistakes and what to check

  • Using the resolution label as the bitrate. Read the profile or measure the port.
  • Subtracting a fixed percent to turn H.264 into H.265. Enter the rate you will run.
  • Adding a sub stream that stays on the access switch, or omitting one that leaves on the uplink.
  • Counting the same stream on the access uplink and again as extra traffic on the aggregation link.
  • Applying × 1.15 to a switch-port measurement that already includes headers, or applying both 1.15 and the planner’s 1.20.
  • Using the peak for a 30-day disk estimate, or the overnight average for the busy-hour uplink, without saying which.
  • Treating a PoE watt pass as proof of remote voltage, or as the camera’s Mbit/s.
  • Calling N-1 passed when the switch has only one uplink.

When the picture stalls or the link is busy, measure one camera’s average and peak on its switch port and list which streams are enabled and where they go. Compare that sum with the uplink counter. If cameras reboot when infrared turns on, check powered-device watts and far-end voltage, not the bitrate.

Limits

This is a planning method. It is not a cable certification, a codec conformance test, or a substitute for the camera datasheet. Multicast that is correctly pruned does not add one copy per viewer; unicast does. Confirm which one you deploy. RAID, filesystem overhead and pre-event recording are extra storage, not included in the 20.736 TB line.

Frequently asked questions

Can resolution alone predict bandwidth for IP cameras?

No. Codec, frame rate, scene motion and the bitrate setting change the result. Use the configured or measured average bitrate for each stream.

Does a PoE power budget calculator give camera network bandwidth?

No. The PoE power budget calculator returns watts, port count and a class limit. Camera network bandwidth is a separate sum of concurrent stream bitrates in Mbit/s.

Can I subtract a fixed percentage when moving from H.264 to H.265?

No. Do not apply a fixed savings percentage. H.264 and H.265 are different standards, and the bitrate still depends on the scene and the encoder settings.
